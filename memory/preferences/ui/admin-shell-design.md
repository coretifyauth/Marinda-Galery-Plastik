# Admin Shell, List View & Detail View — Design Reference

## Sumber

Supersede reference lama (HRMent card-dashboard style — lihat git history file ini kalau perlu balikin). Acuan sekarang: pola visual & struktural **ERPNext/Frappe desk**, bukan konten HR-nya — pola list-view/detail-view generic-nya yang dipake buat entity kita (Account, Journal Entry, dst).

Kenapa ganti: ERPNext dirancang buat data operasional padat (banyak baris, banyak field, banyak entity terkait) — cocok sama sifat data akuntansi (COA bisa ratusan akun, journal entries ribuan baris). Pola card-dashboard HRMent lebih pas buat data personal (1 staff = 1 halaman rich), bukan buat tabel transaksi.

## 1. App Shell

- **Sidebar kiri persisten, ramping** — logo+nama app di atas. Di bawahnya list modul, tiap modul = 1 baris icon+label, flat (bukan kartu).
- **Grouped by functional area, bukan flat list rata** — begitu jumlah route lebih dari ~5-6, sidebar dikelompokkan pakai section label kecil (`text-xs uppercase text-slate-400`) + 1 icon per grup, **collapsible** — klik label grup toggle expand/collapse (chevron rotate, state di client component, **default semua collapsed** biar sidebar ringkas pas pertama load). Grouping sekarang: **Accounting** (`Calculator` — Chart of Accounts, Journal Entries, General Ledger), **Accounts Receivable** (`Wallet` — Customers, AR Invoices, AR Payments), **Accounts Payable** (`CreditCard` — Suppliers, AP Bills, AP Payments), **Inventory** (`Boxes` — Items, Stock Position, Purchase Orders, Goods Receipts, BOM, Production Orders, Goods Issues). Modul baru masuk grup yang sesuai; kalau gak ada grup yang cocok, bikin grup baru + icon baru — jangan taruh flat di luar grup manapun.
- **Item aktif**: background abu-abu muda (`bg-slate-100`) di baris itu + teks jadi warna aksen/bold — bukan garis vertikal tebal, bukan pill.
- **Top bar tipis** — kiri: breadcrumb (`Module / List / Detail`). Kanan: search global (icon kaca pembesar, expand jadi input), lalu **Documentation** (icon `BookOpen`, link ke `/docs`), lalu notifikasi, lalu avatar+nama user (dropdown: profile/settings/logout). Top bar TIDAK berat/tinggi — ERPNext top bar cuma ~48-56px, beda dari HRMent yang lebih tebal.
- **Sidebar khusus modul bisnis/akuntansi (Domain Roadmap), bukan tempat untuk link meta/utility — KECUALI Settings.** `/docs` (knowledge base) sengaja TIDAK masuk sidebar — itu bukan modul transaksional, hidup di top bar kanan (icon `BookOpen`, persis di kiri avatar user). **Settings beda** (diperbarui 2026-08-12, preferensi user, supersede catatan lama yang taruh Settings di top bar) — dipindah ke **bottom sidebar, posisi fixed** (bukan ikut scroll list nav di atasnya, bukan ikut collapsible group manapun): `<nav>` daftar modul dapet `flex-1 overflow-y-auto` (scroll internal sendiri kalau daftar modul kepanjangan), lalu di bawahnya `<div className="shrink-0 border-t ...">` isi 1 link "Settings" (icon `Settings` dari `lucide-react`, `href="/settings/charges"`) — sejajar styling item nav biasa (`bg-slate-100` + teks aksen kalau `pathname.startsWith("/settings")`). Top bar kanan sekarang cuma sisa "Documentation" + avatar, gak ada icon Settings lagi di situ (dihapus, jangan duplikat 2 tempat).
- Breadcrumb selalu ada, bahkan di halaman list (`Accounting / Chart of Accounts`) — bukan cuma muncul di detail page.
- **Sidebar posisi fixed terhadap viewport — gak boleh ikut ke-scroll pas konten discroll.** Implementasi: shell terluar `h-screen overflow-hidden` (bukan `min-h-screen`), sidebar-nya sendiri `h-screen overflow-y-auto` (biar list nav-nya sendiri yang scroll internal kalau kepanjangan, bukan seluruh halaman), dan kolom konten (`main`) yang dapet `overflow-y-auto` buat scroll independen. Pola ini berlaku di app shell utama (`(app)/layout.tsx` + `sidebar.tsx`) DAN di shell dokumentasi (`docs-shell.tsx` + `doc-explorer.tsx`) — dua-duanya butuh treatment yang sama karena struktur sidebar+konten-scrollable-nya identik.
- **Lebar sidebar `w-64` (256px)**, naik dari `w-56` semula (2026-08-12, preferensi user). Karena sidebar `fixed` (bukan flex item beneran), kolom konten harus dikasih `pl-64` yang sama persis di `(app)/layout.tsx` biar gak ketiban timpa — dua nilai ini WAJIB selalu sinkron manual (gak ada satu sumber kebenaran/CSS variable buat lebar ini), kalau salah satu diubah tanpa yang lain, konten bakal ketiban sidebar atau nyisain gap kosong.
- **Konten halaman (wrapper terluar tiap page/detail view) full-width, TIDAK dibatasi `max-w-*`** (2026-08-12, preferensi user — sebelumnya tiap halaman punya wrapper `max-w-3xl`/`4xl`/`5xl` yang gak pernah didokumentasikan, cuma pola yang nempel dari awal). Wrapper-nya sekarang `className="flex w-full flex-1 flex-col gap-6"` — `w-full` + `flex-1` biar ngisi penuh sisa lebar viewport setelah sidebar, konsisten di semua halaman list & detail. Yang TETAP dibatasi lebarnya: dialog `<Modal>` (prop `maxWidth`, biasanya `max-w-2xl`/`3xl`/`4xl`) — modal form emang harus tetap ringkas, beda konteks dari halaman penuh.

## 2. List View — pola default buat semua data tabular

Ini pola utama ERPNext, dipake di HAMPIR SEMUA index halaman kita (`/accounts`, `/journal-entries`), gantiin pola card-grid lama.

- **Toolbar tipis nempel langsung di atas tabel** (bukan di atas page): kiri judul list ("Chart of Accounts") + count badge (jumlah row), kanan sederet tombol kecil — `+ New` (primary, paling menonjol), Filter, Sort, Refresh, kolom-visibility (opsional). Semua tombol kecil (`text-sm`, padding tipis), bukan tombol besar.
- **Filter sidebar kiri** (di dalam content area, bukan app sidebar) — opsional, muncul kalau user klik "Filter" atau kalau list-nya emang butuh (COA butuh filter by category/normal_balance). Kolom sempit (~200px), isi checkbox/dropdown per field yang bisa difilter.
- **Tabel padat**: baris pendek (`py-2`, bukan `py-4`), font `text-sm`, border cuma horizontal antar baris (`border-b border-slate-100`) — TIDAK ada border vertikal antar kolom, TIDAK ada shadow per-row. Header kolom: `text-xs font-medium text-slate-500 uppercase`, background sedikit beda (`bg-slate-50`), sticky waktu scroll.
- **Checkbox kolom pertama** tiap baris (buat bulk-select/bulk-action) — konsisten di semua list view, walau belum ada bulk action jalan (siapin strukturnya).
- **Klik baris (bukan icon) navigasi ke detail** — seluruh row clickable, hover kasih `bg-slate-50`.
- **Pagination/infinite scroll** di bawah tabel, bukan di tengah page — kompak, cuma "Load more" atau angka halaman kecil di kanan bawah.
- List view TIDAK pakai kartu putih rounded per baris data (beda dari pola lama) — datanya tabel murni di dalam 1 container putih besar.

## 3. Detail/Form View — pola buat 1 entity (Account detail, Journal Entry form)

- **Header row di atas** (di luar body form): breadcrumb + **judul generik halaman** (mis. "AP Bill Details" — BUKAN nama/kode entity spesifik, itu pindah jadi baris data di body) + `flex justify-between`, tombol aksi yang scope-nya ke SELURUH entity (`Batalkan`, `Delete`, dst) rata kanan sejajar judul. Diperbarui 2026-08-12 (preferensi user) — sebelumnya judul header pakai nama entity spesifik (mis. "CV Sumber Plastik — SP-001"), sekarang itu jadi salah satu row biasa di body (field "Supplier"/"Rujukan Dokumen").
- **Body form — 2 pola tampilan field, pilih sesuai kebutuhan**:
  - **Pola lama** (field kecil dikit, form yang bisa diedit langsung): 2 kolom per baris (label kecil abu-abu di atas, input/value di bawah), 1 section polos dalam 1 container putih, dipisah cuma divider/spacing.
  - **Pola baru — "grouped label-value rows"** (2026-08-12, preferensi user, dipakai buat tab "Detail" halaman read-only kayak AP Bill): komponen `src/components/ui/detail-rows.tsx` (`<DetailRows groups={[{title, rows: [{label, value}]}]}>`) — tiap grup punya judul (mis. "Informasi Bill", "Ringkasan"), rows-nya baris label(kiri, background abu-abu `bg-slate-50`, bold)-value(kanan, polos) dipisah divider tipis horizontal, grup disusun 2 kolom berdampingan (`lg:grid-cols-2`, jadi 1 kolom di layar sempit). Cocok buat data read-only yang banyak field pendek (tanggal, status, nominal) — bukan buat form yang lagi diedit.
- Field yang locked/published (lihat `state-naming-convention.md`) ditampilkan read-only dengan style abu-abu + ikon gembok kecil, bukan disembunyikan.
- Untuk entity yang cuma punya 1-2 child table kecil yang gak lepas dari transaksi utamanya (mis. `journal_lines` di Journal Entry — harus keliatan bareng pas review balance debit=credit), tetap **tabel inline di bawah form utama**, bukan tab.
- **Tab wajib dipakai begitu entity punya BANYAK tabel referensi/relasi** (2026-08-12, preferensi user, supersede catatan versi lama yang bilang tab cuma buat `/accounts/[id]`) — pola sebelumnya (numpuk semua tabel relasi vertikal di 1 halaman, kayak `/ap-bills/[id]` yang tadinya punya 6 tabel bertumpuk: Jurnal, Pembayaran, DP, Retur, Tukar Barang, Write-off) diganti jadi 1 tab per tabel relasi. Komponen: `src/components/ui/tabs.tsx` (`<Tabs tabs={...} active={...} onChange={...}>`, controlled, styling mirror tab ad-hoc `/accounts/[id]`).
  - **"Detail" BUKAN tab** (dikoreksi 2026-08-12, sesi yang sama) — field/info card milik entity itu sendiri (`<DetailRows>`, termasuk field derived/ringkasan kayak Jumlah/Terbayar/Retur/Outstanding di AP Bill) langsung tampil di body, di ATAS tab strip, selalu keliatan gak peduli tab relasi mana yang lagi aktif. Tab strip cuma isi tabel-tabel relasi.
  - Tiap tabel relasi (`ap_payments`, `ap_credit_notes`, dst) jadi 1 tab sendiri, label tab-nya rangkap fungsi count-badge (gak perlu lagi span "judul tabel + count" terpisah di atas tabel, itu udah keliatan di tab strip).
  - **Tombol aksi yang scope-nya ke 1 tabel relasi tertentu (retur, tukar barang, terapkan DP, dst) pindah ke DALAM tab itu** — posisinya rata kanan di atas tabelnya (bukan lagi numpuk semua di header kanan atas). Contoh: tombol "Retur — Kurangi Utang" cuma muncul di tab "Retur — Kurangi Utang".
  - **Tombol aksi yang scope-nya ke SELURUH entity (bukan ke 1 tabel relasi tertentu), kayak "Batalkan"/"Delete", TETAP di header** — sejajar judul generik halaman, gak ikut pindah ke tab manapun, karena dia gak "milik" tab tertentu.
  - Pilot pertama: `/ap-bills/[id]` (2026-08-12) — urutan body: header (judul generik + aksi entity) → `<DetailRows>` (Informasi Bill, Ringkasan) → `<Tabs>` 6 tab tabel relasi (Jurnal, Pembayaran, DP Diterapkan, Retur — Kurangi Utang, Tukar Barang, Tulis-jadi-Beban).
  - **Rollout selesai ke SEMUA halaman detail** (2026-08-12, sesi yang sama) — 21 halaman sisanya (`/accounts`, `/customers`, `/suppliers`, `/items`, `/ar-invoices`, `/ar-deposits`, `/ap-deposits`, `/ap-return-credits`, `/ar-return-credits`, `/journal-entries`, `/ar-payments`, `/ap-payments`, `/purchase-orders`, `/goods-receipts`, `/sales-orders`, `/goods-issues`, `/production-orders`, `/bom`, `/stock-opnames`, `/fixed-assets`, `/pos-sales`) semua dikonversi ke pola yang sama: header generik + `<DetailRows>` + (`<Tabs>` kalau ≥2 tabel relasi, tabel inline kalau cuma 1). Diverifikasi bersih lewat `tsc --noEmit`, `eslint`, dan `next build` (production build) di semua 22 halaman — 0 error. **`/ap-payments`, `/ar-payments`, `/ap-return-credits`, `/ar-return-credits` sebagai halaman terpisah kemudian dihapus total** (2026-08-12, langkah lanjutan sesi yang sama) — lihat submodule "Konsolidasi Halaman Anak ke Induk" di bawah.

## Detail Page — ATURAN WAJIB (bukan lagi case-by-case)

**Keputusan user (per percakapan sesi ini, supersede catatan "dipicu kebutuhan riil" versi lama):** tiap tabel yang punya child/related table (1-ke-banyak — invoice punya payment+retur+DP, deposit punya application+forfeiture, journal entry punya lines, dst) **wajib** punya halaman detail `[id]`, dan **aksi transaksional apa pun** terhadap baris itu (retur, batalkan, terapkan, hanguskan, posting, dsb) **wajib hidup di halaman detail itu**, bukan inline di row list. Ini sekarang default buat entity baru — bukan sesuatu yang ditunggu sampai "kerasa butuh".

Entity yang **sudah** ikut aturan ini penuh (retrofit selesai 2026-08-07, `memory/scope-debt/ui-detail-page-retrofit.md` sudah dihapus): `/accounts/[id]`, `/customers/[id]`, `/suppliers/[id]`, `/items/[id]`, `/ar-invoices/[id]`, `/ar-deposits/[id]`, `/ap-bills/[id]` (aksi "Batalkan" dipindah dari row list ke sini), `/journal-entries/[id]`, `/purchase-orders/[id]`, `/goods-receipts/[id]`, `/production-orders/[id]`, `/bom/[id]`, `/goods-issues/[id]`, `/fixed-assets/[id]` (aksi "Posting Penyusutan" dipindah dari row list ke sini). Semua list-nya sekarang murni klik-baris-ke-detail, gak ada tombol aksi apa pun nempel di row. (`/ar-payments/[id]` dan `/ap-payments/[id]` sempat ikut aturan ini juga, sekarang dihapus total — lihat submodule "Konsolidasi Halaman Anak ke Induk" di bawah.)

- **Pola implementasi**: tiap route `[id]` punya `page.tsx` (Server Component tipis, cuma `await params` — Next 16 `params` selalu `Promise` di Page component) yang render `view.tsx` (Client Component, isi logic query+UI-nya, nerima `id` sebagai prop biasa). Bukan bikin 1 file client langsung baca `params` via `use()`.
- **Row klik navigasi** ditambahkan di halaman list yang punya detail page (poin 2 di atas, "Klik baris navigasi ke detail") — seluruh `<tr>` clickable, TIDAK ada lagi tombol aksi apa pun di row list begitu detail page-nya ada (beda dari pola lama `fixed-assets` yang masih nyimpen "Posting Penyusutan" di row — itu pola LAMA yang sekarang dianggap gak sesuai aturan).
- **Tab wajib begitu entity punya banyak tabel relasi** — lihat poin 3 di atas ("Detail/Form View") buat detail pola tab + ke mana tombol aksi pindah. Diperbarui 2026-08-12, supersede catatan lama yang bilang tab cuma buat `/accounts/[id]`.
- **Semua aksi transaksional (retur, batalkan, terapkan, hanguskan, posting, dst) hidup DI detail page** — row list jadi murni browse-only, gak ada tombol aksi apa pun di row-nya. Aksi yang scope-nya ke 1 tabel relasi hidup di tab-nya masing-masing; aksi ke seluruh entity (Batalkan, dst) tetap di header. `/ar-invoices/[id]` (Retur, Batalkan) adalah contoh pertama yang udah bener sesuai aturan "aksi hidup di detail page", sebelum pola tab-nya ada.
- **Breadcrumb rute dinamis**: `Topbar` (`src/components/topbar.tsx`) di-generalize — kalau `pathname` gak match persis `routeLabels`, dicek prefix (mis. `/accounts/abc-123` cocok prefix `/accounts`) lalu breadcrumb jadi `[Label List, "Detail"]`. Gak fetch nama entity di topbar (topbar komponen global, gak punya akses ke data halaman) — breadcrumb generic "Detail" cukup, nama entity udah ada di `<h1>` halaman itu sendiri.

## Konsolidasi Halaman Anak ke Induk (2026-08-12, preferensi user)

**Keputusan**: entity yang secara struktural SELALU "anak" dari 1 entity lain (1 baris anak = wajib nunjuk balik ke 1 induk spesifik, gak pernah berdiri sendiri secara bisnis) gak perlu punya sidebar menu + list page + detail page terpisah — cukup jadi tab (atau sub-section di dalam tab) di halaman detail induknya. Tujuannya murni mengurangi jumlah menu sidebar, bukan soal database — tabelnya di database TETAP ada, cuma UI-nya yang dilebur.

**Yang dilebur**: `/ap-payments` (list+create+detail) dan `/ap-return-credits` (list+detail) dihapus total, fungsinya pindah ke `/ap-bills/[id]` — tombol "Bayar" (buka modal, isi `record_ap_payment`) sekarang ada di tab "Pembayaran", dan sub-tabel "Piutang Retur Supplier" (+ tombol "Refund Tunai" per baris, `refund_ap_return_credit`) muncul di bawah tabel credit note di tab "Retur — Kurangi Utang" (cuma tampil kalau ada return credit buat bill itu). Padanan AR: `/ar-payments` dan `/ar-return-credits` dihapus total, fungsinya pindah ke `/ar-invoices/[id]` — tombol "Bayar" di tab "Pembayaran" (`record_ar_payment`), sub-tabel "Saldo Kredit Retur Customer" (+ "Refund Tunai", `refund_ar_return_credit`) di tab "Retur" (data-nya reuse `customerReturnCredits` yang emang udah di-fetch buat form "Ganti Barang", di-filter ke `credit_note_id` milik invoice itu — gak query baru).

**Kenapa aman dilebur (bukan sembarang page bisa)**: AP Payment selalu `bill_id not null` (1 payment = 1 bill spesifik, gak pernah lepas). AP Return Credit selalu lahir dari 1 `credit_note_id` yang nunjuk balik ke 1 `bill_id` (excess retur otomatis, gak ada form "bikin baru" independen — satu-satunya aksi manusia di situ adalah "Refund Tunai"). Sama persis polanya di AR. Beda dari entity kayak Suppliers/Customers yang punya banyak anak lintas beberapa induk berbeda (1 supplier byar banyak bill) — itu TETAP punya halaman sendiri, gak bisa dilebur ke "1 bill tertentu" karena datanya emang lintas-bill.

**Konsekuensi struktural**: `lib/ap-payments/schema.ts`, `lib/ap-return-credits/schema.ts`, `lib/ar-payments/schema.ts`, `lib/ar-return-credits/schema.ts` (type + `recordApPaymentSchema`/`refundApReturnCreditSchema`/dst + fungsi derive kayak `returnCreditRemaining()`) **TETAP ADA** — cuma route `app/(app)/ap-payments/**` dkk yang dihapus, modul lib-nya diimpor langsung dari halaman `[id]/view.tsx` induknya. Sidebar (`src/components/sidebar.tsx`) dan breadcrumb (`src/components/topbar.tsx` `routeLabels`) ikut dibersihin dari 4 entry itu.

## Settings (`/settings/charges`) — tab per section

Halaman Settings numpuk beberapa section gak berhubungan langsung (Default Akun, Preset Akun Aset Tetap, 3 katalog Kategori Tambahan POS/AR/AP, Pengaturan Pajak) — begitu section-nya nambah jadi 4+ konsep beda, ditumpuk vertikal jadi kepanjangan/susah dinavigasi. Dipecah jadi `<Tabs>` (komponen sama yang dipakai detail page relasi, poin 3 di atas — bukan kasus baru, cuma reuse) per KELOMPOK KEPENTINGAN, bukan 1 tab per komponen: **Default Akun**, **Aset Tetap**, **Kategori Tambahan** (3 `CatalogManager` POS/AR/AP digabung 1 tab karena sama-sama "katalog kategori tambahan", cuma beda modul), **Pajak**. Beda dari aturan wajib tab di detail page (poin 3, yang tabnya 1:1 sama tabel relasi) — di sini pengelompokan berdasar kedekatan concern, bukan 1:1 tabel.

## Kapan dipakai, kapan enggak

- List view (poin 2): default buat semua index/listing halaman data (`/accounts`, `/journal-entries`) — TAPI kalau tabelnya punya children, row list gak boleh punya tombol aksi, cuma klik-ke-detail.
- Detail/form view (poin 3): wajib buat tabel yang punya child/related table (lihat aturan wajib di atas). Aksi transaksional selalu di sini.
- App shell (poin 1): berlaku di semua halaman tanpa kecuali.
- Landing/dashboard halaman ringkasan (kalau nanti dibikin, misal financial report overview) boleh pakai kartu ringkasan/stat tile — itu bukan list data mentah, jadi gak wajib ikut pola tabel.
